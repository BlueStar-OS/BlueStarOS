eMMC 为什么需要时钟

  eMMC 接口本质上是同步总线协议（基于 MMC/SD 规范）。所有数据传输都靠 CLK 信号来采样：

  - 主控（SoC 的 eMMC 控制器）驱动 CLK 线，eMMC 芯片在时钟边沿采样 CMD/DATA 线
  - 没有时钟就没法区分 bit 边界 — 和 UART 不同，eMMC 没有起始位/停止位这种自同步机制
  - 时钟频率决定传输速率：HS400 模式下 CLK=200MHz，双沿采样，DATA 8-bit 宽 → 理论 400MB/s

  RK3588 上 eMMC 的时钟来源是 CRU（Clock & Reset Unit）里的 PLL 分频链：

  GPLL/CPLL → cclk_emmc (卡时钟，给 eMMC 芯片)
             → hclk_emmc (AHB 总线时钟，给控制器寄存器访问)
             → bclk_emmc (数据通路时钟)

  所以"全局时钟"其实是指 SoC 的时钟树必须先初始化好，eMMC 控制器才能工作。U-Boot/内核启动早期如果没配好 CRU，eMMC
  控制器寄存器都读不了。

  硬盘控制器是什么

  硬盘控制器是 SoC 内部（或 PCB 上）的硬件模块，负责把 CPU 的内存读写操作翻译成存储协议的命令序列：

  ┌──────────────┬────────────────────┬──────────────────────────────────────────────┐
  │   存储类型   │       控制器       │                     协议                     │
  ├──────────────┼────────────────────┼──────────────────────────────────────────────┤
  │ eMMC         │ DWMMC / SDHCI      │ MMC 命令集（CMD0/CMD1/CMD17/CMD18...）       │
  ├──────────────┼────────────────────┼──────────────────────────────────────────────┤
  │ SD 卡        │ 同上               │ SD 命令集（和 MMC 大部分兼容）               │
  ├──────────────┼────────────────────┼──────────────────────────────────────────────┤
  │ NVMe SSD     │ PCIe + NVMe 控制器 │ NVMe 命令队列（Submission/Completion Queue） │
  ├──────────────┼────────────────────┼──────────────────────────────────────────────┤
  │ SATA HDD/SSD │ AHCI 控制器        │ ATA 命令（READ DMA EXT 等）                  │
  ├──────────────┼────────────────────┼──────────────────────────────────────────────┤
  │ virtio-blk   │ virtio MMIO        │ virtqueue 描述符链                           │
  └──────────────┴────────────────────┴──────────────────────────────────────────────┘

  以 RK3588 的 eMMC 为例，控制器是 Synopsys DesignWare MMC (DWMMC)：

  CPU → AXI/AHB 总线 → DWMMC 控制器 (MMIO 寄存器)
                            ↓
                       CMD 线 + 8-bit DATA 线 + CLK
                            ↓
                        eMMC 芯片（内部有 Flash 阵列 + FTL）

  CPU 写控制器的 CMDARG 寄存器 + CMD 寄存器 → 控制器自动在总线上发出命令帧 → eMMC 芯片响应 → 数据通过 DMA 搬到内存。

  控制器和块设备的关系

  用户空间:  read("/dev/sda1", buf, 4096)
                ↓
  VFS 层:    文件系统(ext4/fat) → 算出逻辑块号 LBA
                ↓
  块设备层:  struct block_device → 请求队列(bio/request)
                ↓
  驱动层:    eMMC 驱动 → 把 LBA 翻译成 MMC CMD17/CMD18
                ↓
  硬件层:    DWMMC 控制器 → eMMC 芯片

  关键概念：

  - 块设备是操作系统的抽象 — 把底层存储统一暴露为"按 LBA 读写固定大小块"的接口
  - 控制器驱动是块设备的底层实现 — 不同控制器（DWMMC、SDHCI、AHCI、NVMe）各自实现 read_block(lba, buf) /
  write_block(lba, buf)
  - 块设备层屏蔽了硬件差异：上层文件系统不关心底下是 eMMC 还是 NVMe，只管按 LBA 读写

  在你的 BlueStarOS 里，virtio_blk 就是 RISC-V/QEMU 平台的块设备驱动。aarch64 真机上需要换成 DWMMC 驱动来访问 eMMC —
  这也是为什么编译 aarch64 时 virtio_blk 找不到的原因，那个模块只在 RISC-V QEMU 平台存在。
